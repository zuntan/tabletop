# Tabletop — AI共有作業机 試作指示書
2026年10月14日 改訂版

## 1. 目的とコンセプト

Tabletopは、人間とAIエージェントが同じ2D空間で資料を共有し、共同で検討するための仮想的な作業机である。

人間はブラウザ上で画像、図形、テキスト、Web資料などを自由に配置・操作する。

AIエージェントはMCPを通じて同じ作業机を参照・操作する。

主な目的は、CLIエージェントと人間との視覚的な意思疎通を容易にすること。

完成した図面や画像を制作すること自体を目的とはしない。資料を広げ、指し示し、比較し、書き込みながら考えるための場所である。

初期の操作感は、簡易的なベクター描画・画像編集アプリケーションに近いものを想定する。

### 基本方針

- 人間とAIが同じオブジェクトと作業状態を参照する。
- AIと人間の操作は、同じ内部操作として処理する。
- 特定のAIモデルやCLIエージェントに依存しない。
- AIのチャットUIや実行環境は提供しない。
- 作業机は一時的な空間であり、永続化を必須としない。
- 初期は2Dに限定する。
- 人間による操作とMCPによる操作は、共通の状態管理・履歴管理を利用する。

## 2. システム構成

システムを大きく2つのパーツに分ける。

### A. MCPサーバー

通常のプログラムとして実行する。

役割は以下のとおり。

- CLIエージェント向けのMCPツールを提供する。
- ブラウザアプリとWebSocketで双方向通信する。
- MCPツールの要求をブラウザに転送し、実行結果を返す。
- ブラウザ内のオブジェクト状態・選択状態・操作履歴を取得する。

初期のMCP接続方式はstdioを想定する。

MCPサーバーは基本的に通信と命令の中継を担当し、作業机の描画・状態管理はブラウザ側が担当する。

WebSocketの要求と応答には対応するIDを付与し、タイムアウト、エラー、切断時の挙動を適切に扱う。

### B. ブラウザアプリ

作業机本体を提供するWebアプリケーション。

- TypeScript / JavaScriptを想定する。
- SVGを中心にした描画を検討する。
- SVG以外の技術も必要に応じて組み合わせてよい。
- マウス・タッチ操作を想定する。
- オブジェクト、選択状態、履歴をブラウザ側で管理する。
- MCPサーバーとWebSocketで通信する。
- 静的Webアプリとして配布できる構成が望ましい。

初期試作では、ブラウザアプリを開いている間だけ作業机が存在する構成でよい。

## 3. キャンバスと基本操作

初期は2Dキャンバスを提供する。

### 基本操作

- オブジェクトの追加・削除
- 単一選択・複数選択
- マウスによる移動
- 拡大・縮小
- Z-orderの変更
- キャンバスのパン・ズーム
- オブジェクトのプロパティ確認・変更
- Undo / Redo

### 基本オブジェクト

- 矩形
- 円・楕円
- 直線・矢印
- テキスト
- ラスター画像（PNG/JPEG/WebP等）
- SVGベクター画像
- iframeによるWebページ表示
- URLリンク

各オブジェクトには一意のIDを付与する。

描画方式とオブジェクトの内部データ構造は分離することが望ましい。

外部SVGは、初期段階では単一オブジェクトとして扱ってよい。内部の個々の図形までプリミティブに展開する必要はない。

Webページのiframe埋め込みがサイト側の制限により失敗する場合は、通常のブラウザでURLを開く手段を用意する。

## 4. AIからの操作

MCPを通じて、作業机の情報取得と変更を行う。

具体的なツール名や分割は実装担当者に委ねる。

### オブジェクト参照

- オブジェクト一覧の取得
- 指定IDの詳細取得
- オブジェクトの種類・位置・サイズ・プロパティの取得
- オブジェクト間の前後関係の取得

### オブジェクト操作

- オブジェクトの追加
- プロパティ変更
- 移動・サイズ変更
- 削除
- 複数操作の一括実行

### ユーザーの選択状態

- 現在の選択オブジェクトIDの取得
- 複数選択状態の取得
- 必要に応じたポインタ位置の取得

人間が「これ」「こっち」「この部分」などと指示したとき、AIが対象を特定する手掛かりとして利用する。

選択状態は、オブジェクトそのものの状態とは区別して管理する。

## 5. 作業机の状態とシリアライズ

作業机全体の状態を構造化データとして扱う。

内部形式はJSONなどを想定するが、厳密な形式は実装時に決定する。

AIは以下の情報を段階的に取得できることが望ましい。

- 作業机の概要（オブジェクト数、種類、revision等）
- オブジェクトの一覧
- 指定オブジェクトの詳細
- 選択状態
- 必要に応じた作業机全体の状態

全オブジェクトの詳細を毎回AIへ送信する必要はない。

画像やSVGなどのバイナリ・大容量データは、オブジェクトのメタデータと分離して扱える構成が望ましい。

全体キャプチャ機能については検討対象とするが、初期試作の必須機能とはしない。

## 6. 状態履歴（History）

**今回の改訂で追加する重要な要件。**

Tabletopの履歴は、人間やAIそれぞれの操作履歴ではなく、作業机そのものの状態変化の履歴とする。

人間による操作も、AIによる操作も、同じ時系列の履歴として扱う。

### 6.1 共通履歴

例えば、以下のような履歴を保持する。

```text
Revision 0 : 空の作業机
Revision 1 : 画像Aを追加
Revision 2 : 矩形Bを追加
Revision 3 : 矩形Bを移動
Revision 4 : 矢印Cを追加
Revision 5 : 画像Aを削除
```

履歴は作業机全体に対して一つとする。

Undo / Redoも、この共通履歴を対象にする。

操作した主体ごとに履歴を分離しない。

### 6.2 操作主体のメタデータ

履歴には、操作主体を識別するメタデータを付与できるようにする。

例えば、

- human
- agent-01
- agent-02

など。

この情報は、履歴表示の色分けや操作の識別に利用する。

ただし、操作主体によって操作権限やUndo / Redoの挙動を変えることは、初期仕様では想定しない。

**履歴は共通、操作主体は付加情報**という関係を維持する。

### 6.3 revisionによる差分取得

AIが作業机の変化を把握できるように、履歴には単調増加するrevisionを付与する。

AIは前回確認したrevisionを指定し、それ以降に発生した変更を取得できるようにする。

例えば、

```text
get_changes(since_revision: 20)
```

結果のイメージ：

```json
{
  "current_revision": 23,
  "changes": [
    {
      "revision": 21,
      "operation": "add",
      "target": "image-007",
      "actor": "human"
    },
    {
      "revision": 22,
      "operation": "move",
      "target": "rect-003",
      "actor": "agent-01"
    },
    {
      "revision": 23,
      "operation": "delete",
      "target": "arrow-002",
      "actor": "human"
    }
  ]
}
```

これによって、AIが毎回キャンバス全体を再取得しなくても、何が追加・変更・削除されたのかを把握できる。

### 6.4 Undo / Redoとの関係

Undo / Redoとrevisionの意味が矛盾しないように設計する。

例えば、Undoを実行した場合でも、新しい状態変更イベントとしてrevisionを進める方式が考えられる。

これなら、revisionは単調増加し、AIは途中の変更を見失わずに済む。

ただし、Undo / Redoの内部実装方式は固定しない。

重要なのは、AIが取得する変更履歴と、現在の作業机の状態が整合していることである。

### 6.5 操作の粒度

マウスドラッグ中のすべての座標変化を履歴に残す必要はない。

通常は、ドラッグ開始から終了までを一つの移動操作として扱う。

複数オブジェクトの追加や一括変更についても、一つの操作グループとして扱えることが望ましい。

履歴がAIにとって意味のある操作単位になるよう配慮する。

## 7. 履歴をAIのコンテキストとして利用する

履歴はUndo / Redoのためだけのものではない。

AIが、作業机上で直近に何が起きたかを把握するための情報源としても利用する。

例えば、

「さっき追加した画像」

「いま動かした矩形」

「最後に消した図形」

「前回確認したあと、何が変わった？」

といった指示に対応できるようにする。

AIは履歴から該当する操作とオブジェクトIDを特定し、必要に応じて詳細情報を取得する。

現在の選択状態と履歴は独立した情報として扱う。

これにより、AIは現在の作業机の状態と、そこに至るまでの変更の双方を参照できる。

なお、履歴だけで曖昧な指示が必ず解決できることを保証するものではない。判断に必要な情報を提供することをTabletopの役割とする。

## 8. Web資料の取り扱い

Web検索、ページ遷移、DOM解析、情報抽出などは、CLIエージェント側の外部ツールに任せる。

Tabletopは、AIが提示した情報を会議机に配置・表示することに専念する。

初期の対応対象は次のとおり。

- URLリンク
- iframeによるページ表示
- 抽出したテキスト
- 外部から渡された画像

Tabletop自体には、Webスクレイピングや汎用ブラウザ自動操作機能を実装しない。

## 9. Mermaidなどの図表との連携

Mermaidを含む外部の図表生成ツールとの連携を考慮する。

初期段階では、生成されたSVGを単一のオブジェクトとして配置できればよい。

将来的には、Mermaidソースを保持して再描画する専用オブジェクトも考えられる。

ただし、初期試作では図表エンジンそのものを内蔵する必要はない。

## 10. ライフサイクルと永続化

Tabletopは一時的な作業空間を基本とする。

- ブラウザ内に作業状態を保持する。
- 閉じれば状態が失われてもよい。
- 保存・復元機能は必須としない。
- 履歴も作業机の寿命に従う。
- AIの会話履歴とは独立させる。
- 外部ファイルの原本は変更しない。

将来的な保存・エクスポート機能は否定しない。

## 11. 初期試作の到達目標

最初の試作では、次の一連の操作が成立することを確認する。

1. ブラウザでTabletopを開く。
2. 人間が画像・図形を追加し、移動する。
3. AIがMCPを通じて現在のオブジェクト一覧を取得する。
4. AIがMCPを通じて図形やテキストを追加する。
5. 人間がオブジェクトを選択する。
6. AIが選択されたオブジェクトを特定する。
7. AIがそのオブジェクトを変更する。
8. 人間がUndo / Redoを実行する。
9. AIが指定revision以降の履歴を取得し、何が変わったかを確認する。

特に、**人間とAIの操作が共通の履歴に反映され、AIがその変化を取得できること**を確認する。

## 12. 初期実装の対象外

- AIモデルの実行・管理
- AIチャットUI
- Web検索エンジン
- ブラウザ自動操作
- 高度な画像編集
- 3D描画
- ユーザーアカウント
- クラウドストレージ
- 永続的なドキュメント管理
- 複数ユーザーの同時編集
- 複数の作業机の同期
- AIの描画過程を再現するアニメーション

## 13. 開発方針

まず、実際にCLIエージェントから利用できる最小構成を実装する。

UIフレームワーク、SVGライブラリ、履歴管理方法、WebSocketメッセージ形式、MCPツールの具体的な分割は、実装担当者の判断に委ねる。

過度な抽象化や将来機能の先行実装は避ける。

最初の目的は、高機能な画像編集ソフトを完成させることではない。

**人間とAIが、同じ作業机を操作し、現在の状態とその変化を共有できることを検証する。**
