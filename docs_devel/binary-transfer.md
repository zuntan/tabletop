# ブラウザ・MCP間の分割転送

2026-11-01の採用仕様。ブラウザ内の画像は従来どおりBase64 Data URLで保持し、転送時だけバイナリへ取り出す。

## 共通上限（十進MB）

|対象|上限|
|---|---:|
|素材1点・生成PNG|10,000,000 bytes|
|manifest・転送の非バイナリ情報|10,000,000 bytes|
|机ファイル・ZIP展開合計・PDF・机間コピー|250,000,000 bytes|
|オブジェクト|3,000個|
|ZIP内エントリ|3,001個|
|WebSocket 1メッセージ|20,000,000 bytes|

操作の内部バッチは、3,000個のピンの属性・接続・シリーズ復元も一度のUndoに収めるため12,000操作まで。オブジェクト総数の3,000個制限は別に適用する。

## 転送手順

`BinaryTransfer` は両方向で共用する。小さな制御JSONを除き、本文はメタデータと生のバイナリ添付へ分離する。PDFのbase64、画像のData URL、机アーカイブをそのままBase64文字列として流さない。

開始情報（転送ID・用途・サイズ・SHA-256）→受付確認→最大1,000,000 bytesずつのチャンク→各チャンク受信確認→終端→全体サイズ・SHA-256検証→完了確認。各バイナリフレームに36バイトの転送IDと4バイトの連番を付ける。1件が完了するまで次の大容量送信を受け付けない。小さな状態通知は通せる。

添付合計250MB、メタデータ10MBに加えて、共通エンベロープ用の4バイトを許容する。机アーカイブ、PDF、コピーには用途ごとの250MB検査も別に適用する。

受信確認が30秒来ない場合、または受信チャンクが30秒来ない場合は中断。終端受信時は検証開始を通知し、送信側の通信待ちタイマーを解除する。総転送時間や生成・検証処理には新しい時間上限を設けない。切断・順序違反・サイズ不一致・ハッシュ不一致では一時データを破棄する。自動再試行・途中再開はしない。

MCP側は受信チャンクを権限0600の一時ファイルへ逐次書込み、受信中に全チャンクをメモリへ蓄積しない。受信後のエンベロープ検証・用途処理時には全体を読み込む。ブラウザはメモリ内で受信・結合する。したがって、分割転送はブラウザの生成・展開・表示に必要なメモリを削減するものではない。

## ファイル処理

SAVEはブラウザの既存`encodeDeskFile`で作った`.tabletop`を送信し、サーバーで検証後、既存の原子的ファイル保存を使う。LOADはサーバーからファイルをそのまま送り、ブラウザの`decodeDeskFile`で検証してから机を置き換える。確認中・転送中・展開中の編集は既存のセッション／リビジョン／文書世代のガードで検出する。

PDFも同じ転送を使い、旧14MiB制限を250MBへ変更。既存のラスタ画素数上限は維持。外部ペースト・画像追加・AI素材追加・カメラなどの生成画像は10MBで検査し、自動縮小しない。元の机は失敗時に置き換えない。

接続時に`binaryTransfer:1`の対応を確認する。旧ブラウザには再読込、旧MCPには再起動を案内する。旧大容量JSONへの自動フォールバックはしない。従来の20MB JSON机転送制限は廃止する。
