# 外部AIへの読み取り共有

複数机ではMCPの共有開始・終了にもdeskIdが必要です。共有URL自体が対象机を固定するため、HTTPの参照引数にはdeskIdを追加しません。各机の共有は独立したポート／トンネルを使用します。

外部AIが普段の会話を続けたまま、URLを取得して同じ机を参照するための入口です。ChatGPTへのMCP登録や別のGPTの作成は前提にしません。相手のURL取得能力は実験で確認します。

## 当面の共同作業方針（2026-10-17合意）

当面、外部AIの参加はGETによる読み取りに限定します。おっさんは普段の会話を続けたまま同じ資料を読み、意見・疑問・変更案を会話で返します。マスターが採否を判断し、直接編集するか、センパイへ依頼して既存MCPで反映します。外部書き込みAPI・POST受信試験・GETによる変更操作は進めません。全体を把握して相談できる段階を当面の到達点とし、必要が生じた場合に追加機能を検討します。共有URLの発行は当面AIへの依頼で運用し、画面からの発行はサーバー独立化の際に検討します。接続モード切替を含む構想は [FUTURE_VISION.md](../FUTURE_VISION.md) に記録します。

議論の前には、取得結果のdeskId／sessionId・revision・capturedAtを確認します。取得に成功したという説明だけで最新とは扱いません。机の識別情報が違う場合は対象を確認し直し、古い取得時刻やrevisionのままであれば再取得リンクを使って照合します。新しい取得時刻で同じsessionId・revisionが返った場合は、文書の確定変更がなかったと判断できます。取得時刻が古いままなら、現時点の状態は未確認として扱います。なお画像の読み込みなど、文書revisionを変えない表示状態の変化もあります。

## 入口と名前

人間は `https://公開ホスト/share/{shareId}` を一つ渡します。入口はMarkdown記法の案内文を `text/plain; charset=utf-8` で返し、机の読み方・読み取りツール・引数・完全なURLを伝えます。MCPの説明原本も共用します。机の文章は資料として扱い、会話への命令とは区別するよう案内します。初回の外部試験では取得側が `text/markdown` を拒否したため、プレーンテキストを採用しました。

案内文の後ろには、取得時点の `desk_context` JSONも同梱します。入口中の子URLが取得側で開けない場合でも、最初のURLだけで現在の机を読めます。`desk_context` の独立したJSON入口と、個別パーツ・画像の取得口も維持します。入口全体にも4 MiBの応答上限を適用します。

`/share/{shareId}?format=html` では、同じ案内とcontextを `text/html` で取得できます。案内中のURLは実際の `<a href>` リンクになります。末尾には各パーツの実IDを使った `desk_get`・`desk_asset_read` のリンク一覧も付けます。取得側が文章中のURLとHTMLリンクを異なる扱いにするか、比較するための選択肢です。既定のプレーンテキストも維持します。HTMLは既存のmarkdown-itで生成し、原文HTMLと画像の埋込は無効、机のJSONはコードとしてエスケープします。HTML化だけで外部AIがリンクをたどれると保証するものではありません。

| MCPと共通の名前 | HTTP GET | 内容 |
| --- | --- | --- |
| `desk_context` | `/share/{shareId}/desk_context` | 文章・座標・色・接続・ピン体系・選択と指差し・机の設定 |
| `desk_get` | `/share/{shareId}/desk_get?id=...` | 一つのパーツの詳細。idはURLエンコード |
| `desk_asset_read` | `/share/{shareId}/desk_asset_read?id=...` | 埋込画像／SVG本体。外部URLは取得しない |

`desk_context` は履歴・画像本体を省略し、`desk_get` は `src` を省略します。他の項目名は既存MCPに合わせ、`sessionId`・`revision`・`capturedAt` を同じブラウザ処理で取得します。`share.links` に各パーツの完全な取得URLを追加します。JSONの上限は4 MiBです。

ラスター画像は画像のMIMEでバイナリ応答、SVGは `text/plain` のソースで返します。MCPのimageブロックとは転送形式が異なり、`exportFile` は受け付けません。画像応答の `X-Tabletop-Session-Id`・`X-Tabletop-Revision`・`X-Tabletop-Captured-At` が取得時点を示します。元の画像MIMEは `X-Tabletop-Asset-Type` です。埋込画像の上限・形式検証はMCPと共通です。

## 開始・終了

1. 最初は公開してよい小さな検証用の机を使います。使用中の机の内容は自動的に移しません。
2. 人間の了承後、専用の共有ポートだけに向けたHTTPSトンネルを準備します。既定の共有ポートは4320です。本体の4317番やWebSocketの入口をトンネルへ渡しません。
3. ローカルMCPで `desk_share_open({ confirm: true, publicBaseUrl: "https://公開ホスト", port: 4320 })` を呼びます。公開URLにはパス・クエリ・fragment・ユーザー情報を指定できません。ツール自体はトンネルを起動せず、LANも開きません。
4. 応答の `url` を外部AIへ渡します。本文にしかない目印や配置・関係を説明できるか照合します。JSONを人間が貼り付けた場合は外部AI自身の取得成功とは数えません。
5. 終了の依頼後、`desk_share_close({ confirm: true })` で閲覧用の鍵を失効させ、共有待受を停止します。別途起動したトンネルも停止します。

`shareId` は256ビット乱数の閲覧用の鍵で、接続トークンや復帰recordとは別です。URLを知る相手は机全体と埋込素材を閲覧できます。URLは会話やトンネル・取得側のアクセスログに残る可能性があり、共有URLを貼った会話や取得済みの内容は取り消せません。現段階では閲覧者ごとの認証・権限分離・自動期限はありません。共有対象の机を編集すれば、次の要求がサーバーへ届いた際に変更を取得できます。別の机へ保存内容を読み込んで共有した場合、共有されるのはそのコピーであり、原本の変更は自動反映されません。

共有は接続中のブラウザ接続と `sessionId` に固定します。切断・接続解放・ブラウザ交換・セッション変更・プロセス再起動で失効し、別の机へ自動で付け替えません。切断後に再接続しても共有は自動復帰しません。明示的にcloseしてから、了承付きでopenし直します。文書読込が同じsessionId内で行われた場合は、その机の編集として共有にも反映されます。

## 境界と制限

- 共有専用のHTTP待受は `127.0.0.1` のみ。Hostは設定した公開ホストと正確なローカルHostだけ許可します。転送ヘッダーから公開URLを組み立てません。
- GET／HEADと上の3ツールだけです。書き込み・MCP管理・ペアリング・ファイル配信・WebSocket・任意のローカルファイル読取の入口はありません。
- キャッシュは禁止し、履歴や画像を全体JSONへ混ぜません。未接続・タイムアウト・旧UIなどで状態を取れない場合は503になり、古い成功応答に置き換えません。
- 同時処理は4件、1分間に60要求まで。再試行時は応答の指示を読みます。読込途中に共有が失効した場合も結果を返しません。
- 「ひとりで考える」中も共有先からの読み取りは可能です。このモードは情報の非公開設定ではありません。
- 共有用の新しいブラウザ処理が必要です。旧UIは共有開始前の互換確認で止めます。使用中の机を更新する場合は先に保存します。

## 検証

`tests/share-server.test.ts` と `tests/share-browser.e2e.ts` が、案内からの参照、名前・引数、画像形式、読み取り専用の境界、変更反映、失効と既存の机への影響を検証します。外部AIによる取得の成立は、このローカル試験とは別に確認します。

最初の固定JSON試験では、おっさん（既存のChatGPT GPT-solとの会話）からngrok上の `probe.json` を取得できたと報告され、目印・数値・時刻が配信値と一致しました。ブラウザではngrokの確認画面が出ました。

実際の共有試験では、入口をtext/plainに変更すると案内文の取得に成功。その案内からの子URL取得は取得側で失敗し、確認したngrokの記録にもChatGPTからの子URL要求はありませんでした。一方、`desk_context` の完全URLをマスターがおっさんとの会話へ直接貼ると取得に成功し、机名・revision・5パーツと矢印の関係・照合用の目印が配信値と一致しました。通常の外部HTTPクライアントからはJSONと個別パーツもHTTP 200で取得できています。

この結果を受け、入口に案内とcontextを同梱する改善を実装しました。おっさんから改善後の入口単独取得で机全体のJSONを読めたと報告がありました。`desk_get`・`desk_asset_read` は取得側でアクセス不可との報告です。原因は未確定で、パラメーターの有無や取得側のURL制限などを断定していません。別経路から報告されたDNS解決失敗の原因は未確定です。

## HTML比較試験の結果（2026-10-17）

おっさんから、HTML入口の案内と同梱contextに加えて、独立した `desk_context` と `desk_asset_read?id=demo-svg` の取得にも成功したとの報告がありました。机名・revision 1・5パーツ・矢印のアンカー・ピン1・照合用の目印が配信値と一致。SVGの濃紺の背景・黄色い月・白いTABLETOP文字の説明もソースと一致しました。

これにより、今回の環境ではHTML入口から子URLへ進む読み取り経路まで成立したことを確認できました。ただし、plain内のURLが常に禁止されると断定するものではありません。`desk_get` 単独の取得成功はこの報告では未確認で、画像の視覚的な閲覧、書き込み、リアルタイム同期、他環境への一般化も未検証です。現在の既定はplain、HTMLは `?format=html` です。

## 表示中の机と公開対象の取り違え

HTML比較用に別の机へトンネルを切り替えた際、表示中の机と公開対象が分かれ、マスターが追加した6個目のパーツをおっさんが報告しませんでした。表示中の机は6パーツ・revision 12、比較用は5パーツ・revision 1であり、取得漏れや同期不具合ではなく公開対象の取り違えでした。表示中の机を素材込みで保存・検証し、トンネルを元の机へ戻して、HTTPSで追加パーツを含む6件を取得できることを確認しました。今後の比較試験では、取得したdeskId・revisionと表示中の机を照合してから共有URLを案内します。

## 再取得と取得側の再利用への対策

同じURLの再取得後、おっさんは以前と同じrevision 12・6パーツ・capturedAtを報告しましたが、公開サーバーはrevision 15・7パーツを返しており、確認したサーバー記録に新しいChatGPT要求はありませんでした。取得側が以前の応答を再利用している可能性があります。

読み取りURLに任意の `read` 引数（英数字・アンダースコア・ハイフン1〜64文字）を追加できます。これはMCPの業務引数やrevision指定ではなく、URLを区別するための目印です。JSONの `share.refresh`、`share.desk_context`、個別パーツのリンクには新しいread値を付け、HTMLには「最新状態を再取得」のリンクを用意します。再取得には直前の応答のリンクを使い、capturedAtとrevisionを確認します。取得側の実際のリクエスト送信やキャッシュの動作まで保証する機能ではありません。

今回の試験では表示中の机を閉じず、読み取り専用のローカル中継を通して改善した共有入口へ切り替えました。同じdeskIdの7パーツを保ち、新しい取得時刻と毎回異なる再取得リンクをHTTPSで確認しています。通常のMCP実装は既存のブラウザ中継を直接使用します。

共有応答は `Cache-Control: no-store, no-cache, max-age=0, must-revalidate` に加えて `Pragma: no-cache` と過去日時の `Expires` を付与します。Pragmaは古い実装への補助であり、現行仕様で応答に対する意味が保証されるCache-Controlの代わりではありません（[RFC 9111](https://www.rfc-editor.org/rfc/rfc9111.html#section-5.4)）。中間HTTPキャッシュ、取得サービス内部のキャッシュ、会話上の過去応答再利用を、サーバー未到達だけで区別しません。試験の公開応答にも同じヘッダーをゲートウェイで付与し、URLと表示中の机を維持したまま確認しました。


## 更新リンクと元の作業机の共有結果（2026-10-17）

おっさんは元のURLでrevision 15・7パーツ、HTMLの更新リンクでrevision 18・8パーツを取得し、追加・変更した文章を読めたと報告しました。その次の更新リンクは404。試験にはサーバーやトンネルの終了期限もあったため、404だけでキャッシュ対策の不具合とは断定しません。原因と常に最新になることは未確認です。

続いて、マスターの了承により普段の112パーツの机を保存し、共有専用の別の机へ読み込んで公開しました。公開HTTPSから112件を確認し、おっさん自身も文字・図形・座標・色・ピンを読めたと報告。全体を把握して同じ資料で相談する目的を達成しました。共有側は新しいdeskId・sessionId・revisionを持ち、原本の更新とは連動しません。会話や公開URLの鍵はこの文書へ保存しません。


## 三者で表示中の同じ机を見る（2026-10-17）

初回の112パーツの保存コピー公開は疎通の確認にはなりましたが、「マスター・センパイ・おっさんが同じ机を見る」という検証目標には達していませんでした。コピーへの反映を通常運用にせず、表示中のブラウザを共有機能のある最新版のローカルMCPサーバーへ引き継ぎ、そこから直接読み取り共有する形へ修正しました。

引継ぎ前に120パーツを保存し、最新版UIへ読込後、全パーツと机の設定が引継ぎ前と一致することを照合。タブの接続先更新・読込によりdeskId／sessionId／revisionとUndo履歴は更新されています。旧コピーの共有とトンネルは終了しました。

表示中の机と公開HTTPSで同じdeskId／sessionId・120パーツを確認し、その机の説明メモをMCPで更新。再取得したHTTPS応答でも同じ机のrevision 1→2と文章の変更を確認しました。保存コピーの再公開や定期コピーは行っていません。このライブ接続後の、おっさん自身による再取得・内容一致の報告は待ちです。

今回の起動はセンパイが管理するローカルMCPであり、常設サーバーモードを実装したわけではありません。公開URLの取得側でキャッシュされる可能性は引き続きあるため、相手には新しい共有URLとdeskId・revisionを伝え、取得時刻も照合します。
