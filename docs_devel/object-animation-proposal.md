# 複数パーツの一括アニメーション案

2026-10-16の相談メモ。**汎用の一括アニメーションは将来案。** 2026-10-20、指差した対象の同一平行移動に限定した[easing](./object-move-easing.md)を先行実装。以下の汎用API案は未実装のまま。

## きっかけ

オレンジの丸を24机上単位ずつ下げ、カメラも同じだけ下げる操作を10回実演した。丸の移動とカメラ操作を交互に20回通信する方式では、利用者には非常に遅く感じられた。これは現行の遠隔操作の実演で、ブラウザによるアニメーションではない。経過時間の計測値は取っていない。

細かいフレームをAIが逐次送るのではなく、**AIが動きの計画を一度渡し、ブラウザが滑らかに実行する**方向を検討する。最初のAI判断・ツール呼び出しが届くまでの待ち時間は、アニメーションだけでは短くならない。

## 今回残す案

- 複数のパーツについて、対象ID・移動先・所要時間・easingを一度に指定する。
- 基本は同じ時点から同時に開始する。開始遅延も指定できる案。
- パーツごとに時間・easingを選べるようにする。
- 必要ならカメラ追従も一括指定する。追従する対象群・倍率の扱いは後で詰める。
- 一連の配置変更は全体で1回のUndoにまとめる方向。カメラは引き続き文書Undoと分ける。
- 即時移動も残す。普通の配置替えで、何がどこへ移ったかを人間が追いやすくする用途にも使う。
- 現行の `desk_execute`／`desk_camera_move` に、このアニメーション指定はまだ存在しない。

## データの形のたたき台

以下は**未実装の説明用データ**。ツール名・キー名・既定値・上限・APIの形は確定していない。

```json
{
  "moves": [
    {
      "id": "part-a",
      "to": { "x": 120, "y": 240 },
      "durationMs": 400,
      "delayMs": 0,
      "easing": "ease-out"
    },
    {
      "id": "part-b",
      "to": { "x": 480, "y": 240 },
      "durationMs": 600,
      "delayMs": 0,
      "easing": "ease-in-out"
    }
  ],
  "camera": { "followIds": ["part-a", "part-b"] }
}
```

位置は既存パーツと同じ机上座標。時間はミリ秒に統一する案。easingはまず `linear`／`ease`／`ease-in`／`ease-out`／`ease-in-out` 等の許可リストを候補とし、任意のJavaScript式・コールバックは受け付けない。Web Animations API等の実装方式の採用はまだ決めない。

## 実装前に決めること

- **状態と履歴**：論理座標をいつ確定するか。表示中の補間座標と読み取り結果・保存内容・Undo/Redoをどう一致させるか。
- **開始と完了**：開始受付の応答と完了通知を分けるか。タイムアウト・切断時に結果を確認できるようにし、不明な操作を自動再送しない。
- **競合と停止**：人間の編集・ドラッグ・「ひとりで考える」切替、別のAI要求、削除、Undo、読込が入ったときに止めるか拒否するか。止めたときの位置・履歴も未決定。
- **検証と制限**：全対象を開始前に検証し、不正ID・重複ID・不正座標・不正easing等で一部だけ動かさない。session／revisionガード、最大件数・時間・遅延も検討。
- **既存の幾何**：線・矢印の両端、接続された線やピン説明の追従、グリッドとの整合。補間途中まで格子へ吸着すると動きが跳ねるため、最終座標と表示途中を区別する。
- **カメラ**：人間のスクロール・パン・ズームを優先し、AIのカメラ操作・追従をキャンセルして自動再試行しない方針を、その後の相談で確認。その後、カメラ単独のパン・ズーム・フォーカスのアニメーションと、人間の入力でその場に止める中断処理を別途実装（稼働未反映）。パーツ移動や継続追従は引き続き未実装。複数対象の追従基準、倍率維持か範囲への追従か、途中停止時の位置・履歴の扱いは引き続き検討する。
- **アクセシビリティ**：動きを減らす設定や即時表示への切替。長い演出で通常の机操作を妨げない。

これらは実装依頼でも確定仕様でもない。次回の相談で範囲を絞る。
