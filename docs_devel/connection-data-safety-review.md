# 接続・復旧時の机の内容保護レビュー

## 位置付け

ペアリング案内改善に伴う安全性レビューの記録。現行の保護と限界、将来の改善候補を区別する。将来候補は実装済みの保証でも、採用決定済みの仕様でもない。

今回実装したのは状態別の `nextAction`・`bootstrapReady`、ツール説明・未接続エラーの案内改善のみ。認証・承認条件・入力Schema・ツール数は変更していない。内容保護機能の追加実装は別途設計・承認する。

基本原則は、通常の接続・再接続で机の内容を維持すること。明示的な文書置換や一時的な机の利用まで禁止せず、大がかりなバージョン管理は今回の対象外とする。

操作手順は [接続とペアリングによる復帰](./connection-recovery.md) を参照。

## 現行実装で確認した保護

机の正本はブラウザ内の `Desk`。サーバーは要求を中継し、ペアリングrecordにオブジェクト・配置・履歴を持たない。再接続時にサーバーの旧snapshotをブラウザへ自動適用する経路は確認していない。

| 操作 | 既存タブの内容と履歴 |
| --- | --- |
| 自動再接続 | 維持。切断中の人間の編集もブラウザ側に残る |
| `desk_pairing_restore` | 復帰相手の登録のみ。文書を置換しない |
| サーバー再起動 | ブラウザのタブが生存する限り維持。サーバーの復旧設定は別途必要 |
| `desk_pairing_open` | 文書は変更しない。ただし以前のペア情報を無効化する |
| 既存タブでの手動再ペアリング | 維持。既存ペアまたは内容がある場合、ブラウザで置換確認を行う |
| `desk_release` | 維持。自動再接続を停止し、ローカル編集・保存を継続できる |

切断時はAIの指示枠を消し、カメラアニメーションを停止するが、文書のrevisionやUndo履歴を初期化しない。古いソケットの応答・終了通知には現在の接続との照合があり、新しい接続の処理と区別する。サーバーは編集要求を自動再送しない。

根拠：`src/main.ts` の `Desk` と接続コールバック、`src/pairing-client.ts`、`src/pairing-server.ts`、`src/server.ts` の `attachBrowser`・`request`。

## 現行の限界

### タブの再読込・終了

ページ起動時には新しい `Desk` を作る。文書の自動永続化や、未保存内容に対する離脱警告は確認していない。サーバーの再起動とページの再読込を混同しない。

- 未保存のままタブを再読込・終了すると、メモリ上の内容と履歴を失う。
- 別タブを開くと別の空の机になる。元の内容が消えたとは限らない。
- 保存ファイルはオブジェクト・設定・埋込画像を保持するが、Undo／Redo履歴やペアリングrecordは保存しない。

根拠：`src/main.ts`、`src/model.ts`、`src/desk-file.ts`。

### 古い認識による編集

`desk_execute.expectedRevision` は任意。指定時はrevision不一致を拒否するが、省略時には古い認識による上書きも実行できる。通常編集には対象sessionを照合する入力がなく、別の机でrevision番号と対象IDが一致すれば、revisionだけでは誤編集を防げない。

これは接続時の自動同期ではなく、接続後にAIが発行する変更要求の保護上の限界。復旧後の再読取りは案内しているが、変更前の状態確認をシステムが必須化しているわけではない。

### Undo／Redoと結果不明の要求

AIのUndoは人間を含む共有履歴の最新操作を取り消す。Undo／Redoにrevision条件はなく、AI自身の操作だけを対象にはしない。

タイムアウト・切断は未実行の証明ではない。実行済みで応答だけ失われる場合がある。自動再送はないが、AIが同じ要求を再発行すれば重複操作になり得る。状態と実内容を確認せず再送しない。

根拠：`src/model.ts` の `execute`・`undo`・`redo`・`dispatch`、`src/server.ts` のタイムアウト・切断処理。

## 明示的な置換・削除との区別

- MCPファイル読込は `confirm: true` と `expectedSessionId`・`expectedRevision` の一致が必須。
- UIファイル読込は置換確認があり、非同期読込中にrevisionが変われば拒否する。
- 文書を検証してから置換し、一回のUndoで直前の文書へ戻せる。ただしタブを失った後の復元保証ではない。
- `desk_execute` による削除・上書きには別途ブラウザ確認はない。
- `confirm: true` はAPI上の明示条件であり、人間が実際に承認したことを技術的に証明する仕組みではない。

根拠：`src/desk-file-tools.ts`、`src/desk-file-controls.ts`、`src/model.ts`。

## 状態別案内との整合性と運用上の注意

`waiting-for-AI` は新規接続と復旧を区別してから操作する。復旧では保持済みrecordをrestoreし、openで代用しない。誤ってopenしても文書そのものは消さないが、以前のペア情報を無効にして自動復帰経路を失わせる。

`paired` はペア情報の登録、`bootstrapReady` は新規受付の準備を示す。どちらも接続成立ではなく、`browserConnected: true` を確認し、その後に現在のsession・revision・実内容を読み直す。

復旧や内容のある机の再接続では、既存タブの接続欄を使うことを優先する。新しい空のタブへの接続を元の机の復元と扱わず、元のタブを再読込・終了しない。案内は安全な操作を促すものであり、内容保護を強制する仕組みではない。

## 将来の改善候補

| 優先度 | 候補 | 影響・注意 |
| --- | --- | --- |
| 高 | 既存タブ優先、空の別机との区別、結果不明時の再読取りをさらに明確化 | 案内・文書・テスト。モデル固有の例外は設けない |
| 高 | 変更要求を対象sessionとrevisionへ結び付ける | 入力Schema・互換性・AI側の手順を別途設計。Undo／Redoも検討対象 |
| 高 | 復旧後の状態確認前に変更を拒否する仕組み | 接続単位の状態管理が必要。単なるreadの有無だけで十分かも検討 |
| 中 | 内容のある机の離脱・再読込警告 | ブラウザ制約があり、強制終了・クラッシュの保護にはならない。一時利用の自由を維持する |

現時点で採用・実装するものではない。自動永続化を検討する場合も、秘密情報の分離、保存容量、保存失敗、復元時の旧状態上書きを別途設計し、単純な自動ロードを追加しない。

## 検証記録と回帰テスト候補

### 今回確認したこと

コード・既存テストをレビューし、独立したメモリ内の `Desk` で以下を確認した。稼働中の机やサーバーには操作していない。

1. 古い明示revisionによる編集は拒否され、最新内容を保持する。
2. revision省略時は古い編集を適用できる。
3. 別sessionでもrevision・対象IDが一致すれば通常編集を適用できる。
4. 文書読込ではsession不一致を拒否し、内容を保持する。

この4項目の確認はレビュー時の一時的な実行であり、今回新しい回帰テストとして追加したものではない。

案内改善の実装時には型チェックと `npm test` の127件が成功。安全性レビュー時にブラウザE2Eは再実行していない。Museでの新しい案内の接続試験は別途必要。

### 既存テストで扱う範囲

- `tests/connection-investigation.e2e.ts`：生成／固定トークンでのサーバー再起動、切断中の人間の編集、誤った復帰recordの拒否、手動再ペアリングでの内容保持。
- `tests/desk-release.e2e.ts`：release後の編集・Undo／Redo・保存、別机への接続と元の机への手動復帰。
- `tests/desk-release.test.ts`：保留要求・旧UI・応答不明時の拒否、古い接続との分離。
- `tests/model.test.ts`：revision競合・原子的変更・共有Undo履歴。
- `tests/desk-file-tools.test.ts`：読込の確認条件・session／revision照合・Undoによる復元。
- `tests/connection-guidance.test.ts`、`tests/connection-info.test.ts`：状態別案内、承認条件、接続とペア情報の区別、ツール数と秘密情報の非開示。

### 将来追加するテスト候補

- 再接続前後のオブジェクト・配置・設定・Undo／Redo履歴の比較。
- 応答喪失時の実行済み／未実行の両ケースと、自動再送がないこと。
- 接続先切替時、同じrevision・対象IDを持つ別机への誤編集防止。
- 復旧後の未読取り状態における変更拒否と、その解除条件。
- 離脱警告の表示、取消による保持、意図的に一時机を終了できること。

新しい保護を導入する際は、現行で許されている挙動を説明するテストと、採用後の拒否を期待するテストを区別する。
