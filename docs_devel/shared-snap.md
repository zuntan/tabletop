# 人間とAIの共通スナップ

## 机の設定と保存

表示グループのボタンは「スナップ」。新しい机と、設定のない旧保存ファイルの既定値は次のとおり。

```json
{ "enabled": true, "interval": 24, "origin": { "x": 0, "y": 0 } }
```

`settings.grid` にON／OFF・間隔・格子の原点を保持し、UI／MCP双方の `.tabletop` に保存・復元する。設定の変更と読込は共通Undo／Redoの対象で、revisionも進む。変更しただけでは既存パーツを再配置しない。読込時も、格子に合わせ直さず保存済みの座標をそのまま復元する。

間隔は机上の単位で、ズームとは独立した有限値1〜100,000。原点の各軸は−1,000,000〜1,000,000。現在のUIはON／OFFのみだが、保存データと処理は別の間隔・原点にも対応する。将来の間隔切替UIはまだ追加していない。

保存形式のversionは1のまま。新実装は `settings.grid` のない旧ファイルを読めるが、旧実装の厳密な設定検証は新フィールドを拒否するため、新しい保存ファイルを旧アプリで開けるとは保証しない。利用者の机を更新する場合は先に旧UIで保存し、了承後にサーバーとブラウザの両方を更新する。勝手なリロードはしない。

新サーバーはMCP編集と画像取り込みの実行前に、ブラウザの `settings.grid` を読み取り確認する。未対応・不正な応答や接続先変更なら、編集を送る前に停止する。新しい指定を旧UIが黙って無視することを防ぐためで、古い机の参照・保存は引き続き可能。編集を自動再送せず、更新時は先に保存する。`tests/bridge.test.ts` では旧UI相当の応答を模擬し、編集要求が一件も届かないことも確認する。

## AIが最初に知ること

`desk_settings`、`desk_context.settings`、`desk_state.settings` の `grid` を読む。設定の更新もrevisionに反映されるため、配置には取得時の `expectedRevision` を付け、競合したら再取得する。

基準点は以下のとおり。

- 通常のパーツ：左上。
- 全種類の連番ピン：番号枠の下中央。地図ピン型なら尖った先端。説明文の長さは関係しない。`label_add` の入力座標は従来どおり枠の左上で、先端の座標へAPIの意味を変更してはいない。
- 線・矢印：自由な各端点。明示した接続先のアンカーは格子より優先し、MCPが画面上の近傍アンカーを勝手に選ぶことはない。
- リサイズ：指定した右下の角。寸法そのものを間隔の倍数にする処理ではない。

格子への丸めは原点を差し引いて間隔で割り、JavaScriptの `Math.round` で最寄りの格子点を選んで戻す。ちょうど中間なら正方向へ丸める。人間の操作とAI操作で同じ関数を使う。

## 配置ごとの指定

`desk_execute` のバッチ引数 `snap` は次の2種類。

- `"desk"`（MCPの既定値）：現在の机のON／OFFに従う。ONなら位置・リサイズ・自由端点を補正し、OFFなら指定値を使う。
- `"exact"`：このバッチだけ格子を回避し、指定値を使う。机全体の設定は変更しない。接続先への追従など、既存の接続ルールは維持する。

`desk_asset_import` も同じ `snap` を受け付け、追加時に適用する。画像の差し替えは従来どおり位置・寸法を変更しない。

```json
{
  "expectedRevision": 3,
  "snap": "desk",
  "operations": [
    { "kind": "add", "object": { "id": "memo", "type": "text", "x": 35, "y": 35, "text": "このあたり" } }
  ]
}
```

初期グリッドなら実際の位置は24,24になる。厳密な35,35へ置く場合は `snap: "exact"` を指定する。全体スイッチをOFFにしてから戻す必要はない。

文字・色・リアクション・シリーズのスタイルだけの変更は再配置しない。単軸の位置変更では、指定していないもう一軸を動かさない。UIの数値プロパティ入力は厳密な入力として扱う。ドラッグで確定した位置やUndoの記録も再度丸めない。

## 複数パーツの移動

バッチ全体が位置だけの `update` で、各パーツの希望移動量が共通なら、基準の一個を格子に合わせ、同じ補正量を全パーツへ適用する。個別に丸めて並びを崩さない。

- 基準は先頭の操作のパーツ。`snapAnchorId` でバッチ内の別のパーツを選べる。
- 全パーツの `x`／`y` を指定する。線の全体移動では `x2`／`y2` も同じ移動量で指定し、接続解除が必要ならBindingを明示的に `null` にする。
- 寸法変更や別種類の操作が混ざる場合、共通移動としては扱わない。異なる希望移動量も個別の配置として扱う。
- `snapAnchorId` がこの条件を満たさない場合は、黙って無視せずバッチを拒否する。

UIではつかんだパーツが基準となり、同じ格子計算で相対位置を維持する。

## 実際に置かれた座標

応答は従来のsummaryに加え、`placement.mode` と `placement.results` を返す。結果を推測せず、この値で次の操作を組み立てる。

各結果には次が含まれる。

- `id`：位置・寸法を指定したパーツ。
- `requested`：既定寸法等を補った希望の幾何。線は旧矩形表現でも端点へ換算する。
- `applied`：バッチ全体の接続解決後の実際の位置・寸法。バッチ内で後から削除した場合は `null`。
- `snapped`：格子計算によって幾何を補正したか。明示Bindingや後続のスタイル操作による差分とは区別する。
- `grid`：その操作で参照したON／OFF・間隔・原点。

同じIDへの操作が複数あれば結果も複数あり、`applied` はいずれもバッチ終了時点の幾何を示す。座標が変わらないno-opでも配置結果を返すが、revisionは増やさない。接続先の変更によって間接的に動いたパーツ全体は通常の変更履歴で確認する。画像の埋込データは配置結果に含まれない。

## 全体設定をAIが変えるとき

```json
{
  "expectedRevision": 4,
  "operations": [
    { "kind": "grid_update", "patch": { "enabled": false } }
  ]
}
```

`patch` には `enabled`、`interval`、`origin: { x, y }` を指定できる。省略した項目は維持する。変更と配置を一バッチに入れた場合も操作順に評価し、後続の配置には更新後の設定を使う。

**AIは、人間から全体変更を依頼されたときだけ `grid_update` を使う。** 細かい配置の都合で頻繁にON／OFFを変えない。これは信頼されたAIクライアントの運用ルールで、actor名を使った権限制御ではない。

## 検証と技術的根拠

- `tests/shared-grid.test.ts`：初期値、読み取りの独立性、補正と回避、Undo、原子的な失敗、全ピン形状、複数移動のUIとの一致、リサイズ、接続優先、旧ファイルと保存復元。
- `tests/shared-grid.e2e.ts`：隔離した実MCP・ブラウザで、既定ON、UI作成、通常配置・厳密配置、数値入力、カスタム間隔・原点、UIドラッグ、画像取り込み、保存・読込・Undoを確認。
- [Zod 3公式](https://v3.zod.dev/)：欠けた設定の既定値、厳密なオブジェクト検証。
- [MDN Math.round](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Math/round)：負数・中間値を含む丸め。
- [MDN SVG patternUnits](https://developer.mozilla.org/en-US/docs/Web/SVG/Reference/Attribute/patternUnits)：机上座標の間隔・原点と格子描画。
