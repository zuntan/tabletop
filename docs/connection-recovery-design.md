# 接続復帰の合意事項（2026-10-15）

**設計整理・未実装。認証の具体方式、ツール名・引数は未決定。**

[接続調査](./connection-investigation-2026-10-15.md) の後の議論をまとめる。調査時の「まずTabletopを常駐化する」という提案は採用せず、以下を現在の方針とする。実装やホスト設定変更の許可を意味しない。

## 前提と目的

- AIが人間と共有する机の起動を案内する。初回はURLを提示して開く。
- MCPホストによるアイドル停止、終了・再起動は起こるものとして扱う。Pi固有の延命処理には依存しない。
- 開いているブラウザの机を保持し、以前ペアリングした相手に限って復帰する。
- Chrome操作など、別ツールでブラウザへトークンを入力することを通常の復帰手段にしない。
- AIなしでの単独起動・再起動は今回は対象外。必要性も含めて将来検討とし、追加を既定路線にしない。

## 用語

- **接続トークン**：サーバーへの接続を許可するための認証情報。
- **ペアリング**：以前に対応付けた机と同じ相手であることを確認する仕組み。接続数が0でも、この確認を省略しない。
- **ペアリング情報**：相手の識別と復帰時の確認に必要な情報の総称。識別子と秘密情報を区別し、具体的な構成・形式は今後設計する。

トークン／ペアリングは通信内容の暗号化を意味しない。HMACは議論中の説明例であり、採用決定ではない。チャレンジ応答、秘密トークン照合等の方式は、安全性・複雑さを比較して選ぶ。

## 初回接続

1. AIが接続URLを提示し、人間またはAIの案内で机を開く。
2. 初回接続として認証し、新たにペアリングする。
3. AIは以後の復帰に必要な接続トークンとペアリング情報を受け取り、継続用の引継ぎでも保持する。机側も自分のペアリング情報を保持する。

初回用の認証と既知の机への復帰は区別する。復帰失敗を理由に、未知の机との初回ペアリングへ自動的に切り替えない。秘密の受渡し・保持先・初回情報の失効方法は、具体方式とともに設計する。

## サーバー停止後の復帰

1. 机は切断を認識しても内容を消さず、保持したペアリング情報で再接続を試す。
2. AIのMCP利用再開でサーバーが起動する。AIは記憶している接続トークンとペアリング情報をMCP経由で指定し、既知の机の復帰を受け付ける状態にする。
3. サーバーは復帰接続のペアリングを検証する。机側からも正しい相手への復帰と確認できる設計を検討する。
4. 正しい相手なら接続を復帰し、AIが現在の机の状態を取得する。
5. 明確に異なるペアなら受け入れず、その机には自動復帰を止めてもらう。プロトコルに合わない要求や認証を満たさない相手は接続を拒否する。

これは目標とする流れであり、現行サーバーがAIからのトークン設定・ペアリング登録を受け付けるという説明ではない。ブラウザからの再試行だけで、停止中のMCPプロセスを起動できるわけでもない。

### 待機と拒否は分ける

- サーバー停止中、またはAIによる復帰受付の準備前：間隔を空けて再試行する。
- ペアリング確認成功：自動復帰する。
- 明確なペアリング不一致：自動再試行を停止し、人間の確認へ移る。
- 必要な情報の紛失等で復帰不能：推測せず、手動接続の手順へ進む。

単なる通信失敗をペアリング不一致と断定しない。準備中・不一致等を安全に通知し、どの応答を信頼して再試行を止めるかも、認証方式の設計に含める。未認証の相手が接続枠を占有しないようにする。

## 内容は一致条件にしない

長時間の思考や人間の編集によって、切断中に内容が変わるのは正常。以前と同じ内容、同じrevisionであることを復帰条件にはしない。

- ペアリングは「相手の確認」。内容のハッシュやsessionIdだけを本人確認に使わない。
- 復帰後の状態取得は「現在の状況の確認」。AIはsessionId・revisionと実内容を読み直してから操作する。
- 切断前の編集要求は自動再送しない。結果不明の場合は実状態を照合する。

## 固定トークンでも同じルール

`TABLETOP_TOKEN` による固定トークンも、接続の入口としての選択肢。サーバー停止を防ぐものではない。

固定・自動生成のどちらでも、今回復帰を許可する机のペアリングを確認する。閉じ忘れた別の机が先に接続を試しても、固定トークンを知っているだけで復帰先の接続枠を取得できない設計とする。

正式なホスト設定で利用者が常駐を選ぶことは妨げない。ただしTabletopが見せかけのMCP操作で利用時刻を更新し、ホストの停止方針をごまかす延命は行わない。接続の生存確認用heartbeatとは目的を区別する。

## 復帰できないときの手動手順

- 開いたままの机は再読込・初期化せず、その内容を保持する。
- 人間が現在の内容を保存する、またはAIが案内する新しい接続トークンを既存の接続欄へ入力して再接続する。
- 手動で別のペアリングへ切り替える場合は、人間がその置換を確認する。
- AIが接続トークンやペアリング情報を忘れた場合も、推測・総当たり・未知の机への自動乗換えをせず、この手順を案内する。

保存済みの机の内容は、AIまたは人間が保存データから読み込んで再開する。文書の保存・読込と接続のペアリングは独立させ、`.tabletop` に接続の秘密を含めない。保存ファイルを読み込んだこと自体を、接続相手の認証には使わない。

## 復帰速度と表示

通常のローカル利用では、**サーバーの復帰受付準備ができてから、数秒程度で再接続**を目安とする。保証時間ではなく、隔離環境で実測して調整する。

- 切断後は最初の再接続を早めに試し、以後は最大5秒程度の間隔を目安にする。具体的なバックオフ・揺らぎ等は未決定。
- 再試行では軽い接続要求だけを送り、机の全内容を毎回送らない。
- サーバーの起動待ち時間と、起動後の復帰処理時間は区別する。
- 黙って途絶えた通信の検知方法・heartbeatの間隔は別途検討する。

| 状態 | 人間への提示方針 |
| --- | --- |
| 通常の切断・自動復帰待ち | 控えめな「AI再接続待ち」。赤い警告や繰り返し通知は出さず、編集は継続 |
| 再接続成功 | 静かに接続済み表示へ戻す。ポップアップ不要 |
| ペアリング不一致等、人間の判断が必要 | 目立つ警告で自動復帰停止を伝え、保存・手動再接続を案内 |

細かい理由や試行状況は接続ペインに置き、普段の机上表示は簡潔にする。旧成功文・旧エラーが現在の状態と矛盾して残らないようにする。

## AI向けツール説明に必要なこと

将来のツール説明では、単に引数を列挙するだけでなく、次を明記する。

- 初回接続で受け取った復帰情報を、引継ぎ・コンテキスト整理でも保持すること。
- 復帰時には以前のペアだけを指定すること。
- 情報紛失、不一致、結果不明時の安全な停止と手動手順。
- 復帰後に現在の机を取得してから操作し、古い編集要求を再送しないこと。
- 秘密を公開文書・リポジトリ・通常の診断ログへ書かないこと。会話履歴で秘密を保持する場合にも漏洩リスクがあること。

AIの記憶を保証する設計にはしない。忘れた場合も、机を保護し人間が復旧できることを優先する。

## 実装前に決める事項

- 認証の具体方式。HMAC／チャレンジ応答の採否も未決定。
- 接続トークン・ペアリング情報の生成、保持期間、ブラウザ側の保持範囲、更新・失効・手動置換。
- AIが保持・指定する情報の形式とMCPツール仕様。秘密を直接渡すか、ハンドル等を使うかも未決定。
- 初回受付と復帰待ちの切替、準備前の応答、複数の古いタブがある場合の扱い、認証前の資源制限。
- サーバー待ち・認証失敗・ペアリング不一致を安全に区別するプロトコル。
- 再試行と無応答検知の時間設定、ログの範囲、旧ブラウザとの互換・移行手順。

認証方式の選定時には公式仕様を確認し、通常の再起動・準備前・不一致・複数タブ・手動再接続・情報紛失・結果不明を隔離環境で検証する。実装開始、実際の机の更新、コミット・pushは別途了承後に行う。
