# 本棚と、机からAIへの呼びかけ

2026-10-18｜マスターを介して受領した、おっさんの構想と相談記録。**未実装。今回はドキュメントと机のカードへの記録だけで、ストレージへのアクセス・通知・バックグラウンド作業は開始しない。**

## 目的

本棚は、外部の資料への参照を保持し、必要な情報を机へ取り出す文具。「AIが使える道具を持っていれば、机の上でできることが増える」という分担を試す。

人間は机で意図を示し、AIは自分の能力で仕事をする。将来はボタン操作をAIへの呼びかけにつなげる。おっさんの表現は **「机越しのアイコンタクト」**。

## 第一段階：本棚の基本機能

### 参照先を持つパーツ

一つのディレクトリ、またはそれに相当する保管場所を、一つの本棚として机に置く。本棚は複数配置できる。

- ローカルのディレクトリ
- Google Driveのフォルダー
- Boxのフォルダー
- その他、エージェントが利用できる保管場所

本棚の机上の配置と、ファイルシステムの階層・位置関係は独立。ディレクトリツリーやファイラーを作る構想ではない。当初の呼び名は「フォルダーカード」だった。

### 一覧と取り出し

当面は読み取り専用。

1. **一覧**：参照先のファイル一覧を本棚に表示する。
2. **取り出し**：選んだテキストファイルの内容を、新しいテキストパーツとして机へコピーする。

取り出した文章は元ファイルと独立した机の情報になる。同期・書き戻しはしない。ここでいう「読み取り専用」は参照先に対するもので、AIが机の本棚一覧や取り出したパーツを更新することは含む。

一覧は明示的に更新した時点のスナップショットでよい。常時最新でなくてよく、机をロードした直後に空でも構わない。自動更新・ファイル監視は不要。

### ストレージにはエージェントがアクセスする

Tabletopは参照先を識別する情報と一覧を保持し、ストレージ別のアクセス処理は持たない。例えばBoxのURLを、エージェントが自分のMCPやコネクタで解釈して利用する。

- ローカルファイルもエージェントがアクセスできる範囲だけ。
- 利用可能な道具がなければ「アクセスできません」でよい。
- Tabletopにストレージ別の認証・アクセス権管理を内蔵しない。
- Tabletop MCP経由で、エージェント自身の権限を超えるアクセスを可能にしない。
- **エージェントが読めることと、共有の机へ掲載することは別。** 一覧のファイル名も含め、共有先・掲載する範囲を意識する。

当面はチャットで「この本棚を更新して」と頼む。AIが参照先を調べ、取得した一覧を本棚へ書く。取り出しもチャットで依頼して構わない。

## 第二段階：机の操作をAIへの依頼にする

エージェント側の対応を確認した後に進める将来段階。複雑な専用通信方式を先に作らず、既存の履歴・revisionとIRQ相当の通知を利用する案。

```text
人間が本棚の「更新」を押す
  → Tabletopが棚更新依頼を記録し、revisionを進める
  → エージェントへ注意喚起の通知（IRQ相当）
  → エージェントが履歴と机を確認
  → 自分のツールで参照先を取得
  → 本棚の一覧を更新
```

履歴が依頼の記録で、通知自体は注意喚起。通知に仕事の全情報を詰め込むものではない。通知を取りこぼしても未確認の記録を取得できる構造を目指す。重複処理は実装時に検討する。

配送方法や、通知後に作業を開始・再開する方法はエージェント側に任せる。Codex・Copilot CLI等で異なるため、今回どれかの対応を前提にしない。バックグラウンド処理や外部要求の受付機構が使える場合は利用し、将来は音声経路でもよい。未対応ならチャットでの依頼を残す。

本棚専用の仕組みに閉じず、ほかの文具にも応用できる人間からAIへの入力経路として考える。

## 今回の対象外

- 元ファイルへの保存・書き戻し
- 常時同期、自動更新、ファイル監視
- ディレクトリツリーやファイラー
- ストレージ別の専用アクセス機能、認証の内蔵
- 特定のエージェントを前提にした通知配送の実装

## センパイからの検討事項（構想への補足・仕様未確定）

以下は受領した構想と区別する、既存構造との照合からの検討事項。

- 本棚名・参照先・一覧の取得時刻・結果／エラー、各資料の識別情報をどう持つか。
- 取り出した文章には、参照先と取得時刻を出典として添えると、独立したコピーであることを理解しやすい。
- 参照先やファイルの本文は外部資料であり、人間からの作業依頼とは区別する。資料内の文章を、そのまま実行すべき命令として扱わない。
- 現在の編集履歴と作業依頼の寿命は同じではない。机の保存ファイルはUndo履歴を保持しないため、未処理依頼をどこまで保存・復帰させるかは別途決める。
- 依頼ID、未確認／実行中／完了／失敗等の状態、確認済み位置を持つ案を検討する。履歴だけで足りるか、別の依頼状態が必要かは未決定。
- 履歴の再取得やUndoで、仕事が意図せず再実行されないようにする。切断中の依頼、重複通知、再試行、失効・取消の扱いも要検討。
- **通知を受信できることと、待機中のAIが自発的に作業を始められることは別。** エージェントごとの能力を確かめる。
- 「ひとりで考える」中の通知や依頼処理の扱いは未決定。既存のAI編集禁止を依頼経由で迂回しない。

## 2026-10-20：依頼された時間だけ待つ案

MCPからAIへ押し込む通知に加え、AIがLong Pollingで変更を待つ方式を検討する。未実装で、常時監視は開始しない。

- 道具案は `desk_irq(timeoutMs, afterRevision, sessionId)`。既に新しい変更があれば即応答し、なければ指定時間まで非同期で待つ。
- 待機中の変更で応答する。通知は現在のrevision等の合図に留め、詳細は既存の履歴で確認する。
- 人間から依頼されたときだけ指定時間で待ち、時間切れなら終了する。自動再待機・無制限ループは行わない。
- 変更に反応するかはAI側の判断。待機の終了と、依頼した仕事の完了は別。
- sessionIdで別の接続・開き直しと区別し、切断・接続先変更・キャンセルでも待機を終了する。
- まず1秒程度・回数制限付きで変更検知を試し、会話との両立は別途実機確認する。
- 現行Tabletopのブラウザ要求は10秒でタイムアウトする。長い待機は既存要求と分けた扱いが必要。
- Codexの待機中の追加発言処理と実消費は未実測。短い周期でAIが呼び直せば、推論・会話履歴・ツール結果の処理が積み重なる。時間切れで止める方式をまず採用候補とする。

参考：公式MCP設定 https://learn.chatgpt.com/docs/extend/mcp?surface=cli 、App Server https://learn.chatgpt.com/docs/app-server 。調査と構想の記録であり、実装済みとはしない。

### 並列会話は必須条件にしない

「1分だけ机の変更を待って、何かあれば教えて」という一回の待機だけでも用途が成立する。待機中に通常の会話を並列で処理できることは採用の必須条件としない。まずは変更時の復帰と時間切れ時の終了を確実にする。指定時間は利用例であり、現在1分待機が実装・検証済みという意味ではない。
