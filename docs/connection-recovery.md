# 接続とペアリングによる復帰

実装仕様。議論の経緯は [合意事項](./connection-recovery-design.md)、原因の調査は [調査報告](./connection-investigation-2026-10-15.md)。サーバーとブラウザの両方が新版であることが必要。

## AIの基本手順

### 新しく机を開く

1. 利用者の新規起動または手動再ペアリングの了承を確認する。
2. `desk_pairing_open({ confirm: true })` で初回受付を開く。
3. `desk_connection_info` で接続URLを取得して案内する。
4. ブラウザが接続したら `desk_pairing_info` を呼び、返された `pairing` の全フィールドを**非公開の継続コンテキストに保持**する。コンパクションや引継ぎでも失わないようにする。
5. `desk_summary`／`desk_context` で机を確認して作業を始める。

サーバー起動直後には初回受付も復帰先も未設定。接続数0だけでは新しい机を許可しない。`desk_connection_info` 自体は参照専用で、受付を開いたりトークンを更新したりしない。

`TABLETOP_TOKEN` 未指定なら、初回認証用トークン付きURLを取得できる。指定時は設定済みトークンを返さず、通常URLと手動入力の案内を返す。ペアリング後の復帰情報はこのenvトークンとは別で、envの秘密をAIへ開示しなくても復帰できる。

### サーバー再起動後、同じ机へ戻る

1. 以前の `pairing` 全体を `desk_pairing_restore({ pairing })` へ渡す。
2. ブラウザからの再試行を数秒待つ。Chrome操作等の別ツールは使わない。
3. `desk_connection_info.browserConnected` で接続を確認する。
4. `desk_summary`／`desk_context` から現在のsessionId・revision・実内容を読み直し、変化を把握してから作業する。

復帰時に `desk_pairing_open` を呼ばない。既に接続済みならrestoreは拒否するので、状態を読んで作業を継続する。結果不明の編集要求は自動再送しない。

机の内容が切断中に変わっているのは正常。ペアリングに内容・revision・sessionIdの一致は求めない。ブラウザの編集・保存・読込は接続待ちでも続けられる。

### 棚を残して接続を解放する

1. 現在の接続を解放して新規・手動接続の受付を開くことについて、利用者の了承を得る。
2. `desk_release({ confirm: true })` を呼ぶ。成功は `{ released: true, waitingFor: "new-pairing" }`。
3. 元のタブは「AI接続解放済み」になり、自動再接続を停止する。オブジェクト・設定・履歴・人間の選択は残り、ローカル編集・保存・読込を続けられる。AIの指示枠だけは消える。タブを再読込しない。
4. 必要なタイミングで `desk_connection_info` の既存の接続情報を案内する。別の棚を開いても、元のタブの接続欄から手動接続してもよい。接続後は新しい `desk_pairing_info` を非公開で保持し、現在の棚を読み直す。

この操作に保存・読込・内容のコピー・同期・棚の台帳・トークン再生成は含まれない。元のペアリングは無効になり、以前のrecordをrestoreして復帰させる用途ではない。保存や移行が必要なら別途判断・依頼する。現在の通信はループバック限定で、別端末・タブレットから接続するネットワーク対応は含まれない。

切断通知を受けたブラウザが自動再接続を停止してから応答し、サーバーは応答確認後に接続枠とペアを解放する。切替開始時に進行中のハンドシェークを無効化し、切替中の接続・MCP要求を拒否する。未完了のMCP要求がある場合は解放自体を拒否するので、その結果を確認してからやり直す。古いソケットの遅れた終了は新しい接続の要求を破棄しない。

未対応の旧UIは切断せず拒否する。先に保存し、了承のうえで別途更新する。通知への応答が3秒以内に確認できない、または応答前に切断した場合も新規受付を開かない。元のタブだけ停止済みの場合もあるため、エラー後は `desk_connection_info` と人間側の表示を確認し、推測で再送・reload・openしない。接続済みのブラウザがない場合は `desk_release` ではなく、了承付きの `desk_pairing_open` を使う。

### 情報を失った／ペアが違う場合

推測や未知の机への自動乗換えはしない。人間に以下を案内する。

- 現在の机を保存する、または既存タブを再読込せず手動で再接続する。
- 既に自動復帰が止まっていてサーバーに接続した机がないことを確認する。
- 了承後にAIが `desk_pairing_open({ confirm: true })` を呼び、新しい初回受付を開く。以前のペアリングは無効になる。
- `desk_connection_info` で取得した初回用トークンを、既存タブの「接続」欄へ入力する。env指定時は利用者が設定済みトークンを入力する。
- 内容のある机や既存ペアのあるタブでは、置換の確認を了承する。机自体は残る。
- 新しい `desk_pairing_info` を取得し、AIの保持している古い復帰情報を置き換える。

接続中の机がある場合、openもrestoreも拒否する。接続中の机を勝手に追い出すためのAPIではない。接続だけを解放する場合は了承付きの `desk_release` を使う。不要なタブの終了は人間と相談し、先に保存する。

## ツール

| ツール | 入力と役割 |
| --- | --- |
| `desk_release` | `confirm: true`。了承後、棚を残して現在の接続と自動再接続を止め、新規・手動接続の受付を開く |
| `desk_pairing_open` | `confirm: true`。新規・手動置換専用。以前のペアを無効にして初回受付を開く。人間の了承が必要 |
| `desk_pairing_info` | 入力なし。`{ pairing: null }` または復帰用の秘密を含むrecordを返す。MCP限定 |
| `desk_pairing_restore` | `pairing` record。再起動後に既知の机だけを復帰先として登録。文書編集は行わない |

`pairing` は `pairId`（UUID）、`token`（256 bit乱数）、`secret`（256 bit共有秘密）。token／secretは64桁の小文字hex。フィールドを改変せず一緒に保持する。これはブラウザのsessionIdでも、文書の一部でも、初回URLのトークンでもない。

接続済みの机、または異なる復帰先を登録済みのサーバーへrestoreするとエラーになる。自動でopenして回避しない。同じrecordを未接続時に再登録することは可能だが、認証中の試行は一度やり直しになる。

## 認証方式と境界

具体方式は実装段階で比較し、**Web Crypto APIのHMAC-SHA-256によるチャレンジ応答**を選んだ。単純に復帰の秘密を再送する方式と比べ、毎回の乱数に証明を結び付けられ、Nodeとブラウザで標準APIを共用できるため。追加依存はない。設計議論の時点でHMAC採用が決まっていたわけではない。

- 初回はURL／手入力トークンと、既存のHost・Originチェックを使う。初回認証された接続にだけ新しいペアを提供する。
- 復帰は `/bridge?resume=1` で行う。URLに秘密を入れず、ペアIDとクライアント乱数で開始する。
- サーバーも乱数を生成し、サーバー役のHMACを返す。机はその証明を検証してから、クライアント役のHMACを返す。サーバーは検証後、接続確定用のHMACを返す。
- 証明対象はプロトコル名 `tabletop-pair-v1`、役割、ペアID、復帰token、双方の乱数を順序固定JSONで符号化したもの。役割はserver／client／readyで分ける。別の方向や接続への証明流用を防ぐ。
- 検証には `crypto.subtle.verify` を使う。共有秘密は初回の提供以外ではWebSocketへ送らない。
- 完全な証明の検証前には、机の接続枠もMCP要求も渡さない。固定トークンでもこのルールは同じ。

これはローカル試作であり、通信全体の暗号化や各文書メッセージの署名ではない。HTTP／wsの初回通信は暗号化されない。信頼済みのローカル環境を前提とし、悪意あるローカルプロセスによるポートの乗っ取り、同一originの侵害、同じ秘密を盗んだ相手への防御を保証しない。外部公開・TLS・複数参加者は別設計。

ペアID不一致のcloseや不正な証明を受けた机は、安全側に倒して自動復帰を停止する。その警告は「正規サーバーが相手の偽物を断定した」という意味ではなく、**相手を確認できなかった**という意味。未認証の相手により復帰を妨害され得るため、警告を根拠に秘密を再送したり、未知の相手へ自動的に再ペアリングしたりしない。

## メモリ・保存・失効

- ペアリングはサーバーと現在のタブのメモリのみ。localStorage、sessionStorage、秘密ファイルには保存しない。
- `.tabletop`、文書snapshot、履歴・Undo、`desk_state` には含めない。保存ファイルの形式version 1も変えない。
- AIがrecordを保持していれば、サーバー再起動後に復帰できる。タブ再読込・終了では机側の情報を失うため、保存データからの再開と新規ペアリングになる。
- 初回ハンドシェークが途中で切れてペアリングが完了しない場合は、初回受付のやり直しが必要なことがある。
- 現在のペアは、明示的なopenによる置換、releaseの成功、またはメモリ破棄まで有効。release後は古い復帰recordを再利用せず、次の接続のrecordに置き換える。経過時間による自動失効は今回設けない。
- AIへ返したrecordは、会話履歴や引継ぎから漏れるリスクがある。公開文書・リポジトリ・机・通常ログへ書かない。AIの秘密保持を保証する仕組みではない。

## 待機・時間・表示

- 復帰先未登録はclose 4000で待機を促す。机の内容や秘密は毎回送らない。
- 不一致や不正なハンドシェークはclose 4003で拒否。正しい机でも相手を確認できなければ停止する。
- 再試行間隔は最初250ms、次に1秒、2秒、以後5秒。通常のclose通知を受けてからの値であり、サーバー起動時間やブラウザの背景タブ制限を含む保証ではない。
- 未認証接続は最大8本、ハンドシェークはサーバー8秒、ブラウザ側9秒で打ち切る。ハンドシェークのアプリケーションメッセージは4096 bytes以下。WebSocket全体の受信上限24 MBは既存のままなので、大きいフレームの受信段階まで低コストを保証するものではない。
- 通常は控えめな「AI再接続待ち」。フッターへ失敗通知を繰り返さず、詳細を接続ペインに表示する。成功は静かに接続済みへ戻す。
- 確認不能時は「接続確認が必要」と目立つ案内を出し、保存または手動接続を促す。
- サーバーは接続・切断時刻、close code、保留要求数、stdin終了／シグナルによる停止理由を記録する。ペアの秘密や文書本文は記録しない。従来どおり、生成トークンの初回URLは起動ログに含まれる。

黙って途絶えた認証済み接続を検知するheartbeatは今回追加していない。closeが届かない状況では即時復帰を保証しない。ホストを延命する見せかけのMCP呼出しも行わない。

## 旧版からの更新

旧ブラウザはペアリングプロトコルを実装していないため、新版サーバーへそのままは接続できない。サーバーだけが更新された場合も旧机を勝手に再読込しない。

1. 旧タブの保存ボタンで最新の机を保護する。切断中でもUI保存は可能。
2. 保存できたことを確認し、人間の了承後にサーバー・ブラウザを更新する。
3. 初回受付を開いて新版で接続し、保存ファイルをUIまたは明示承認付きMCP読込で戻す。
4. 新ペアのrecordを保持し、内容を照合する。

既存タブの更新は実装とは別作業。今回の隔離試験は実際の机を更新したことを意味しない。
