# 外部AIへの読み取り共有

外部AIが普段の会話を続けたまま、URLを取得して同じ机を参照するための入口です。ChatGPTへのMCP登録や別のGPTの作成は前提にしません。相手のURL取得能力は実験で確認します。

## 入口と名前

人間は `https://公開ホスト/share/{shareId}` を一つ渡します。入口はMarkdown記法の案内文を `text/plain; charset=utf-8` で返し、机の読み方・読み取りツール・引数・完全なURLを伝えます。MCPの説明原本も共用します。机の文章は資料として扱い、会話への命令とは区別するよう案内します。初回の外部試験では取得側が `text/markdown` を拒否したため、プレーンテキストを採用しました。

案内文の後ろには、取得時点の `desk_context` JSONも同梱します。入口中の子URLが取得側で開けない場合でも、最初のURLだけで現在の机を読めます。`desk_context` の独立したJSON入口と、個別パーツ・画像の取得口も維持します。入口全体にも4 MiBの応答上限を適用します。

| MCPと共通の名前 | HTTP GET | 内容 |
| --- | --- | --- |
| `desk_context` | `/share/{shareId}/desk_context` | 文章・座標・色・接続・ピン体系・選択と指差し・机の設定 |
| `desk_get` | `/share/{shareId}/desk_get?id=...` | 一つのパーツの詳細。idはURLエンコード |
| `desk_asset_read` | `/share/{shareId}/desk_asset_read?id=...` | 埋込画像／SVG本体。外部URLは取得しない |

`desk_context` は履歴・画像本体を省略し、`desk_get` は `src` を省略します。他の項目名は既存MCPに合わせ、`sessionId`・`revision`・`capturedAt` を同じブラウザ処理で取得します。`share.links` に各パーツの完全な取得URLを追加します。JSONの上限は4 MiBです。

ラスター画像は画像のMIMEでバイナリ応答、SVGは `text/plain` のソースで返します。MCPのimageブロックとは転送形式が異なり、`exportFile` は受け付けません。画像応答の `X-Tabletop-Session-Id`・`X-Tabletop-Revision`・`X-Tabletop-Captured-At` が取得時点を示します。元の画像MIMEは `X-Tabletop-Asset-Type` です。埋込画像の上限・形式検証はMCPと共通です。

## 開始・終了

1. 最初は公開してよい小さな検証用の机を使います。使用中の机の内容は自動的に移しません。
2. 人間の了承後、専用の共有ポートだけに向けたHTTPSトンネルを準備します。既定の共有ポートは4320です。本体の4317番やWebSocketの入口をトンネルへ渡しません。
3. ローカルMCPで `desk_share_open({ confirm: true, publicBaseUrl: "https://公開ホスト", port: 4320 })` を呼びます。公開URLにはパス・クエリ・fragment・ユーザー情報を指定できません。ツール自体はトンネルを起動せず、LANも開きません。
4. 応答の `url` を外部AIへ渡します。本文にしかない目印や配置・関係を説明できるか照合します。JSONを人間が貼り付けた場合は外部AI自身の取得成功とは数えません。
5. 終了の依頼後、`desk_share_close({ confirm: true })` で閲覧用の鍵を失効させ、共有待受を停止します。別途起動したトンネルも停止します。

`shareId` は256ビット乱数の閲覧用の鍵で、接続トークンや復帰recordとは別です。URLを知る相手は机全体と埋込素材を閲覧できます。URLは会話やトンネル・取得側のアクセスログに残る可能性があり、共有URLを貼った会話や取得済みの内容は取り消せません。現段階では閲覧者ごとの認証・権限分離・自動期限はありません。原本の机を編集すれば、次の取得でその変更も見えます。

共有は接続中のブラウザ接続と `sessionId` に固定します。切断・接続解放・ブラウザ交換・セッション変更・プロセス再起動で失効し、別の机へ自動で付け替えません。切断後に再接続しても共有は自動復帰しません。明示的にcloseしてから、了承付きでopenし直します。文書読込が同じsessionId内で行われた場合は、その机の編集として共有にも反映されます。

## 境界と制限

- 共有専用のHTTP待受は `127.0.0.1` のみ。Hostは設定した公開ホストと正確なローカルHostだけ許可します。転送ヘッダーから公開URLを組み立てません。
- GET／HEADと上の3ツールだけです。書き込み・MCP管理・ペアリング・ファイル配信・WebSocket・任意のローカルファイル読取の入口はありません。
- キャッシュは禁止し、履歴や画像を全体JSONへ混ぜません。未接続・タイムアウト・旧UIなどで状態を取れない場合は503になり、古い成功応答に置き換えません。
- 同時処理は4件、1分間に60要求まで。再試行時は応答の指示を読みます。読込途中に共有が失効した場合も結果を返しません。
- 「ひとりで考える」中も共有先からの読み取りは可能です。このモードは情報の非公開設定ではありません。
- 共有用の新しいブラウザ処理が必要です。旧UIは共有開始前の互換確認で止めます。使用中の机を更新する場合は先に保存します。

## 検証

`tests/share-server.test.ts` と `tests/share-browser.e2e.ts` が、案内からの参照、名前・引数、画像形式、読み取り専用の境界、変更反映、失効と既存の机への影響を検証します。外部AIによる取得の成立は、このローカル試験とは別に確認します。

最初の固定JSON試験では、おっさん（既存のChatGPT GPT-solとの会話）からngrok上の `probe.json` を取得できたと報告され、目印・数値・時刻が配信値と一致しました。ブラウザではngrokの確認画面が出ました。

実際の共有試験では、入口をtext/plainに変更すると案内文の取得に成功。その案内からの子URL取得は取得側で失敗し、確認したngrokの記録にもChatGPTからの子URL要求はありませんでした。一方、`desk_context` の完全URLをマスターがおっさんとの会話へ直接貼ると取得に成功し、机名・revision・5パーツと矢印の関係・照合用の目印が配信値と一致しました。通常の外部HTTPクライアントからはJSONと個別パーツもHTTP 200で取得できています。

この結果を受け、入口に案内とcontextを同梱する改善を実装しました。おっさんによる改善後の入口単独取得と、`desk_get`・`desk_asset_read` は未確認です。別経路から報告されたDNS解決失敗の原因は未確定です。
